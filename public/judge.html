How the shop counted, what the split rule would suggest, and the limits

How the shop counted. Customers paid by bank transfer (VietQR); an order counts as paid only after the shop's accountant matched the money received to the order code. Meta records which ad started each chat; staff write that ad group's code into the order book, then match it against payments and refunds. That matching is done by hand today; it is the step Paid Signal does from PayPal's records. The figures are reported by the author from the order book and the ad account; the shop confirms them and agreed to publish its book (1,214 invoices, 735 payments, 30 refunds, anonymised customer ids, in docs/proof); the ad account's own exports are no longer accessible. "Money" is revenue after refunds, before product, delivery and fees.

What Paid Signal would suggest. Its split rule (proposeSplit, the same code as the demo: paid orders kept per dollar of spend, refunds excluded, order value not used) gives A 53.8% → 17.3%, B 28.8% → 46.3%, C 17.3% → 36.4%. That is an illustration, not a measured lift or an optimal allocation; which moves the budget agent may make is a separate rule (supportedMoves). A person decides, and Paid Signal does not change a live Meta budget. The shop's payments did not go through Paid Signal or PayPal: the shop is why it exists, not a result of it. Numbers: merchant-case-2026-10.json.

The shop's book, run through Paid Signal's own ledger code

735 bank transfers and the 30 refunds from its refund book, fed to the same reconcile() the demo uses, give 705 paid orders kept and 1,317M VND, the same as the shop's reconciliation workbook. Its 7 double transfers are held: each was the same amount sent again for the same order code, 4 to 31 minutes later. A shop paid by bank transfer can run its own book the same way, in the browser: /audit.

Method and limits

A: 145 orders, 254M VND · B: 390 orders, 741M VND · C: 170 orders, 322M VND. This checks the arithmetic, the refunds and the order matching, not judgement or ad causality. For bank transfers the ledger holds the same amount sent again for one order code whatever the gap (7 of 7), and never pairs two different order codes. Without order codes it falls back to the time rule (same payer, same ad, close together): 2 of 7 with the 10-minute checkout window, 7 of 7 with the 60-minute window bank transfers now get, a window set after reading this book. Every customer in this book ordered once, so false alarms cannot be measured on it; unit tests cover one customer's two orders, a split payment and a repeat beyond the window.
